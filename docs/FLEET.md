# Fleet Deployment

Notes for encrypting several M-series boxes rather than one. The dangerous part
is not the encryption — it is how you *provision* the boxes beforehand.

---

## Order of operations, per box

LUKS is the **last** step, not the first:

1. **Fresh-install** Fedora Asahi Remix. Do **not** `dd`-clone another box — see
   the UUID section below. A fresh install gives each machine its own unique
   partition, btrfs and EFI UUIDs.
2. **Restore user-space** onto the fresh install: reinstall the package set, add
   third-party repos and flatpaks, then rsync your tooling and configs.
3. **Re-wire services** that a file-level restore leaves half-configured.
4. **Encrypt** with `luks-deploy.sh` from the live USB.
5. **Post-encryption**, run `post-encryption-setup.sh` and install the boot guards.

> **Never restore another box's `/etc/fstab`, `/etc/crypttab`,
> `/etc/kernel/cmdline`, `/etc/default/grub`, `machine-id`, or `/boot`.** Those
> encode the *source* machine's disk identity. Let the fresh install own them —
> `luks-deploy.sh` rewrites fstab, crypttab, cmdline, GRUB and BLS from the
> *target* box's live UUIDs.

Restoring a large `/home` is best done from a text console with the GUI stopped,
so a live desktop session cannot overwrite restored config files when it exits.
Setting `systemctl set-default multi-user.target` and rebooting is more reliable
than `systemctl isolate multi-user.target` against a running Wayland session.

## UUID uniqueness — the multi-box footgun

Every box should have unique disk UUIDs. Here is where each one comes from:

| UUID | Uniqueness source | Risk |
|------|-------------------|------|
| LUKS2 header UUID | Freshly generated by `luksFormat` on every run | **None** — always unique per box |
| btrfs filesystem UUID | **Preserved through encryption** by design | **High if you clone.** Every box restored from the same image shares one btrfs UUID → collisions when two drives are attached at once, and UUID-based fstab/GRUB become ambiguous |
| Partition PARTUUIDs / EFI UUID | Set when the partition table is created | **High if you `dd`** a whole disk between boxes |

**Rule: provision each box by fresh install plus file-level restore, never by
imaging one box onto another.** Fresh install gives unique btrfs and partition
UUIDs automatically; `luks-deploy.sh` then layers a unique LUKS UUID on top.

If you genuinely must clone an image, re-stamp the target **before its first
boot**:

```bash
btrfstune -u /dev/<part>      # new btrfs UUID (filesystem must be unmounted)
sgdisk -G    /dev/<disk>      # randomise the GPT disk GUID and all partition GUIDs
# then fix /etc/fstab, /boot/loader/entries/*.conf and the EFI entries to match
# the new UUIDs BEFORE booting it
```

Verify before encrypting: `blkid` on the target must not match any other live
box, and the btrfs UUID must differ from the backup source machine.

## Per-box pre-flight checklist

- [ ] On **AC power** (the script enforces AC or >50% battery).
- [ ] Backups current **and independently verified** — actually browse or restore
      from one.
- [ ] Target root is the intended btrfs partition — confirm with `lsblk -f`.
- [ ] Target btrfs UUID is **unique** versus the backup source box (clone check).
- [ ] `/boot` (ext4) and EFI (vfat) present and unencrypted.
- [ ] **No second USB required.** The header always goes to
      `/boot/luks-header-backup.img` and pre-encryption state to the script's own
      directory. The V8 "USB copy" check is a warning, not a gate.
- [ ] The kit is reachable from the live environment.
- [ ] You know your passphrase policy, and will pair any later `luksChangeKey`
      with the argon2id flags (see [RECOVERY.md](RECOVERY.md#passphrase-change)).

## Keeping crypto parameters identical across the fleet

The KDF is pinned in the script rather than left to `cryptsetup`'s auto-benchmark
specifically so that every box matches. Left to its defaults, `cryptsetup` picks
sha256 and a *time-benchmarked* memory cost that varies with how fast the machine
happens to be that day — so two identical Macs would end up with different
security parameters.

If you deliberately vary it for smaller-RAM boxes, record which box got what.
Vary the *memory cost* only — every box stays on argon2id, never pbkdf2:

```bash
sudo LUKS_PBKDF_MEMORY=1048576 LUKS_PBKDF_ITER=8 ./bin/luks-deploy.sh   # ~2 s unlock
```

Audit any box afterwards:

```bash
sudo cryptsetup luksDump /dev/nvme0n1p6 | grep -A6 'Keyslots:'
```

## After each successful encrypted boot

- The LUKS UUID is new on every box — update anything that pins it.
- Run `post-encryption-setup.sh`, then copy the recovery bundle from
  `/root/LUKS-RECOVERY-<host>-<date>/` to secure **offline** storage. Label it
  with the hostname; the bundle README already records the device, LUKS UUID and
  btrfs UUID.
- Take a fresh backup immediately, so the encrypted box has its own first
  snapshot containing the correct `crypttab` and `fstab`.

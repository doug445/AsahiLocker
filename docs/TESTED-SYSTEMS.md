# Tested systems

The machines behind the ✅ claims: every row here has had a real in-place
encryption by `luks-deploy.sh` and boots from it, or an end-to-end run of the
script on a disk image that was then booted — with what was found on the way.
Nothing is listed on the strength of a dry run or a unit test alone. Same
format as [linux-backup-system's](https://github.com/doug445/linux-backup-system/blob/main/docs/TESTED-SYSTEMS.md).

| Fedora Asahi Remix 45 Minimal (aarch64) | **A virtual machine, not a Mac**: a KVM guest on the M2 Max above, running the official Fedora Asahi Remix 45 Minimal image (with a login user, a serial console and `gdisk` added) on a 4096-byte-sector virtio disk, as Apple NVMe presents, 16k-page kernel 7.2.12-402.asahi, SELinux enforcing, edk2 firmware in place of m1n1/U-Boot | the stock Asahi layout exactly as the installer writes it: vfat EFI, ext4 `/boot`, btrfs root with `root` + `home` subvolumes, shim → GRUB, BLS entries, dracut | **end-to-end ✅ — 2026-11-20, 2.2.1**: `ram-rescue.sh build --arm`, reboot into the RAM rescue, `asahilocker --defaults` with a deliberately mismatched passphrase first (asked again, nothing written), `aggressive` profile in 4096-byte sectors, `ALL CHECKS PASSED (12-point gate)`, encrypted boot with the passphrase, `post-encryption-setup.sh`, the boot guards, `ram-rescue.sh remove`. **2.1.0, 2026-11-19**: the same route with the power cut in mid-encryption, then repair and resume from the rescue. The third audit's thirteen findings were reproduced and verified fixed here, released script and fixed script side by side. **3.1.0, 2026-11-25**: the same route for issues #8 and #9. The system encrypted by the 2.2.1 run booted with 54 files without an SELinux label while its deploy log said `SELinux contexts OK`; encrypted again from the rescue with 3.1.0, it booted with none, no denials, and `restorecon -n` finding nothing to change in anything the deploy wrote. `post-encryption-setup.sh` labeled the 2.2.1 system's files, and `--keep-splash-off` left the splash off across a second run without the option. **4.0.0, 2026-11-27**: the same route from the `ready` snapshot with a plain swap file on `/boot` added to the fstab: the new swap check named it and stopped the run until `swap` was typed; a dry run as an 8 GB Mac would see it offered `moderate` as the default and selected it; `ALL CHECKS PASSED`, encrypted boot, and `post-encryption-setup.sh` flagged the same swap file as unencrypted. On that system: 3.1.0's boot guards upgraded in place, then a real `grub2-mkconfig -o /boot/efi/EFI/fedora/grub.cfg`, which Fedora's own refusal did not stop (it looks for `EFI/fedora-asahi-remix/`), wrote a 263-line config over the 3-line stub, and the guard had the stub back within 29 ms. With the machine powered off, the initramfs, the stub and a new `.efi` on the EFI partition were changed from the host; at the next boot the stub guard restored the stub and the boot tripwire reported all three. What a VM cannot show is the Apple boot chain: m1n1, U-Boot and the internal keyboard are not in it. On Apple hardware the RAM rescue has been run on a 14" MacBook Pro (M2 Max), which is what issues #7 to #9 report; the image check of #7 was reproduced on the M2 Max above with the script's own loop against that Mac's sysfs (3.0.0 refuses `simple_pm_bus`, 3.1.0 passes and still refuses an image without `nvme-apple`) |

Eight suites run on every push, 179 checks in all (177 on the CI runners). The loopback suite
(`tests/loopback-core-test.sh`, 43 checks, 41 on the aarch64 CI runners): shrink, in-place
reencrypt with the script's exact flags, header and content survival,
recovery-key enrolment with the AF hash pinned, resume after `--init-only` and
after a hard kill (`cryptsetup repair`), 4096-byte sectors on a 4Kn and a
512-byte device, the GPT-tail alignment run by the script's own function, and
a passphrase refused at the prompt, which must write nothing. With it:
`multi-install-selection-test.sh` (the partition menus on a two-install disk,
12), `luks-mount-test.sh` (a loop-image install, plain and encrypted, 13),
`cli-smoke-test.sh` (every script's command line, 34),
`uboot-efivar-test.sh` (14), `deploy-checks-test.sh` (the default KDF profile per
Mac, the plain-swap check and the lower-case typed confirmations, 30),
`boot-tripwire-test.sh` (16) and `boot-guards-test.sh` (the guards installed over
3.1.0's under a real systemd, an overwrite undone, a re-run, removal, 17). None
of these is a boot.
